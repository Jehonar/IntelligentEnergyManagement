## Abstract

This report describes a web application for monitoring hourly energy use and producing short-term consumption forecasts. Historical readings are stored in SQL Server and shown on a Vue.js dashboard. Forecasts are produced by a Random Forest regressor that runs as a small Python service. The ASP.NET Core API sits in the middle: it serves the data, calls the model, stores the result, and turns the forecast into a simple high/moderate/normal/low recommendation.

The implementation is complete enough to demonstrate the full path from database to chart to prediction. What this report adds, compared with a setup guide, is the reason for the design, a short review of related work, how the model was trained and scored, and how the system was checked. The data used for training is synthetic. That choice made development possible without a smart-meter feed, but it also means the accuracy numbers should not be read as proof that the same model would work on a real building.

## 1. Introduction

### 1.1 Purpose of the application

Energy bills are hard to manage if the only information available is a monthly total. By the time the invoice arrives, the expensive hours are already in the past. Building managers and even households need a view of *when* energy is used, not only *how much* was used over a long period.

The application built for this project has two jobs. The first is ordinary monitoring: list readings, filter them by date and device, and show totals and charts. The second is a forecast for a given hour, using a few inputs (hour, weekday, month, outdoor temperature, and the previous consumption value). After a forecast is produced, the user can ask for a short text recommendation. The text is not generated by a language model. It is based on how far the predicted kWh sits from the historical average in the database.

The Moodle example project was a collaborative task app with AI insights. The same idea is used here, but in a different domain. Instead of tasks and assignments, the “objects” are energy readings, predictions, and recommendations. The example also listed login, mobile clients, and cloud deployment. Those items were treated as optional. Section 4 explains why login was left out.

### 1.2 Why this topic

A lot of energy software only plots the past. Forecasts are useful because they give a chance to change behaviour *before* the peak (shift laundry, lower HVAC, switch off idle computers). Machine learning is a reasonable tool for that, because consumption is not a straight line. It depends on time of day, whether it is a weekend, and temperature.

I did not try to build a full utility-grade EMS (Energy Management System). Those products include meters, billing, alarms, and often a historian database. The goal here was a working student system that still has a real architecture: a browser client, a REST API, a relational database, and a separate process for the model.

### 1.3 Objectives

1. Store and display hourly consumption for several devices.
2. Train a regression model that maps a small set of features to kWh.
3. Expose the model through an HTTP endpoint so the web API does not have to run Python inside .NET.
4. Compare the forecast with the historical average and return a recommendation category.
5. Keep the user interface simple enough that a non-technical user can complete a prediction in a few clicks.

### 1.4 Methodology (how the work was organised)

Work followed a fairly standard student-project sequence rather than a formal Scrum board.

**Analysis.** I listed the screens the demo needed (dashboard, table of readings, prediction form, recommendation list) and the data each screen would show. Functional requirements were written as short statements (FR1–FR8 below). Non-functional ones were limited: local run, response time good enough for a demo, Swagger for the API.

**Design.** The stack was fixed early: Vue 3 for the UI, ASP.NET Core 8 for the API, SQL Server for storage, FastAPI + scikit-learn for the model. The split is not accidental. .NET is a normal choice for a course that already uses C#. Python is the usual place for scikit-learn. Putting both in one process would have been possible (for example with ML.NET), but then the model would be harder to retrain and inspect.

**Implementation.** Database script first, then API endpoints, then the Python service, then the Vue pages. Git was used for version control.

**Evaluation.** The model was scored with MAE, RMSE and R² on a held-out 20% of the synthetic rows. The application was checked manually through the UI and through Swagger. There are no automated unit-test projects in the repository yet; that is a gap and it is discussed in Section 8.

Adding many use-case diagrams would not change the product. Three flows cover almost all of the demo.

**UC2 – Request a forecast.** Actor: operator. Opens AI Prediction, fills the form, submits. The API calls `/predict` on the Python service (or the fallback), saves a row in `Predictions`, and the page shows the kWh value.

## 2. Literature review

This is not a full survey of the energy-informatics field. It is enough to show where the project sits and why Random Forest was a defensible choice for a course project.

### 2.1 Energy monitoring systems

Commercial and research EMS tools typically combine metering, visualisation and sometimes optimisation. For a student project the interesting part is the *data path*: timestamped kWh, optional weather, aggregation by hour/day/month, and a UI that does not hide the numbers behind too many menus. Dashboard design in this work is conventional (KPI cards + line/bar charts), which matches what most monitoring products already do. The extra piece is the forecast form.

### 2.2 Data-driven forecasting of building energy

Olu-Ajayi et al. (2023) reviewed 63 studies on data-driven building energy prediction. They note that SVM, ANN and Random Forest often beat simple statistical models such as linear regression or ARIMA, but that **no algorithm wins in every setting**. Sample size, building type and the energy end-use (heating, cooling, total electricity) all change the ranking. That is a useful warning for this project: a high score on one generated dataset does not mean Random Forest is “the best” method in general.

Ahmad, Mourshed and Rezgui (2017) compared Random Forest and a feed-forward ANN on hourly HVAC data from a hotel. ANN was slightly better on RMSE, but they still recommend RF when the data mix categorical and numeric fields and when the modeller does not want a long tuning process. RF also handles missing values more comfortably. Those arguments match the constraints here: few features, mixed types (hour, weekday, month), and limited time for hyperparameter search.

Alsharif, Rizi and Gürsel Dino (2024) used Random Forest on simulated heating/cooling loads. With around 100 trees they report very high R² (on the order of 0.99) on that simulated data. High R² on simulation is common because the “physics” in the simulator is consistent. The same pattern appears in this project’s synthetic generator: the labels are produced by known rules plus noise, so a tree ensemble can recover most of the signal.

Amasyali and El-Gohary’s line of work, and later reviews such as Olu-Ajayi et al., also stress **temporal granularity**. Hourly models are a different problem from annual energy-use intensity. This application is hourly, which is why hour-of-day is an explicit feature.

### 2.3 Ensemble methods versus deep learning

Olu-Ajayi and other reviews mention XGBoost and neural nets as strong alternatives. Deep models (LSTM and newer time-series networks) can win when there is a long real history and the lag structure matters. For 90 days of generated hourly rows, a deep network would be easy to overfit and harder to explain in a short report. Random Forest with 100 trees and `max_depth=10` is a middle ground: non-linear, standard in scikit-learn, fast to train on a laptop.

Recommendations in this app are **not** a second ML model. They are thresholds on predicted kWh versus the mean. That is closer to a rule engine than to “AI insights” in the Moodle example. I still discuss them under the AI chapter because they are the action that follows the forecast. Mixing a learned regressor with hand-written rules is common in industry (model scores a risk, rules decide the message).

### 2.4 What was taken from the literature, and what was not

| Topic in the literature | In this project |
|-------------------------|-----------------|
| Real smart-meter traces | Not used; generator + SQL seed |
| Weather as a driver of HVAC load | Temperature is a feature |
| Calendar effects (weekend, hour) | `dayOfWeek`, `hour`, `month` |
| Deep learning / LSTM | Not used |
| Occupancy or “number of guests” | Not used |
| Login and multi-user collaboration | Not implemented |

The main honest gap versus published papers is the **data source**. Papers that report MAE in kWh on a hotel or campus are not comparable to MAE on a script that invented the kWh values.

## 3. Application architecture

### 3.1 Overview

Four runtime pieces:

```
Browser (Vue 3 + Vite, port 5173)
        |
        |  REST / JSON
        v
ASP.NET Core 8 Web API (port 5000)
        |                      |
        | EF Core              | HTTP JSON
        v                      v
SQL Server              FastAPI + scikit-learn
IntelligentEnergySystem        (port 8000)
```

The browser never talks to Python or to SQL Server directly. That keeps CORS and connection strings in one place and makes it possible to swap the model later without touching Vue.

### 3.2 Communication

- Vue uses Axios against `http://localhost:5000`.
- The API uses EF Core against `IntelligentEnergySystem`.
- `PredictionService` uses `IHttpClientFactory` (`AiService` client, base URL from configuration, default `http://localhost:8000`, timeout 30 seconds).
- POST `/api/prediction` forwards the same fields to POST `/predict`.
- CORS on the API allows the Vite origin `http://localhost:5173`.

### 3.3 Layering inside the API

Controllers are thin. `EnergyController`, `PredictionController` and `RecommendationController` call services. Services contain queries and the fallback logic. Models map to tables; DTOs are what JSON looks like. This is ordinary ASP.NET structure, not a full Clean Architecture with extra assemblies. For the size of the project, one API project is enough.

### 3.4 Database

Three tables (script: `Database/CreateDatabase.sql`).

**EnergyReadings** — `Id`, `ReadingDate`, `ReadingHour` (0–23), `EnergyConsumption`, `Temperature`, `DeviceName`, `CreatedAt`. Indexes on date and device. Seed: 1 January 2026 – 31 March 2026, four devices, hourly rows (on the order of 8,640 readings).

**Predictions** — date, hour, predicted kWh, created timestamp.

**Recommendations** — optional `PredictionId` FK, message (max 500 chars), type (`HIGH` | `MODERATE` | `NORMAL` | `LOW`).

The ML training CSV (`AI-Service/data/energy_data.csv`) is a **second** synthetic set (2,160 hourly rows, 90 days, no device column). It is generated in `app/model.py`. The SQL seed and the Python generator follow similar peak/weekend/temperature ideas but they are not the same file. That is a design smell: the dashboard and the model are not guaranteed to describe the same building. For a demo it is acceptable; for a real deployment one pipeline should feed both.

### 3.5 How a prediction travels through the system

1. User submits the form on `/prediction`.
2. Vue POSTs JSON to `/api/prediction`.
3. `PredictionService` POSTs to Python `/predict`.
4. FastAPI runs `RandomForestRegressor.predict` on a 1×5 vector.
5. kWh comes back; API inserts `Predictions` and returns id + value.
6. Optional: Vue POSTs `/api/recommendations` with `predictionId` and `predictedConsumption`.
7. `RecommendationService` reads the average from `EnergyReadings`, picks a type, stores the message.

If step 3 throws (service off, timeout, non-success status), the API logs a warning and uses `FallbackPredict`: scale previous consumption (or 10 if missing) by hour, temperature and weekend factors. The UI does not currently tell the user that fallback was used. That should be mentioned in a viva if asked.

## 4. User registration and authentication

The Moodle example spends a whole section on registration, JWT and privacy. This application **does not implement accounts**.

Reasons:

- The demo is single-user on a local machine.
- Adding Identity, password hashing and JWT would have eaten time that was needed for the model and the charts.
- There is no personal data about real people in the seed; the readings are invented.

What this implies:

- Anyone who can reach port 5000 can read and write predictions.
- That is unacceptable on a network.
- A follow-up would add ASP.NET Identity or JWT, HTTPS, and per-user (or per-building) data.

Secure storage of the SQL connection is currently Windows authentication in `appsettings.json` (`Trusted_Connection=True`). Secrets should not be committed if SQL logins are ever used.

This section is therefore a **scope decision**, not a missing homework item that was forgotten in the code.

### 5.1 Devices and seed behaviour

Devices: HVAC, Lighting, Appliances, Computers. The SQL loop raises base load in the morning (around 6–8) and evening (18–21), lowers night hours, and applies extra factors per device (HVAC is the heavy one). Temperature in the seed is a rough seasonal value, not a weather-station series.

## 6. AI-powered insights

### 6.1 What is “AI” here

Only the kWh forecast is a trained model. Recommendations are if/else on ratios. Calling the whole product “AI” would be overselling. The honest description is: **supervised regression + rule-based advice**.

### 6.2 Training data

`generate_training_data(n_days=90)` in `app/model.py` starts at 2026-01-01. For each hour it:

- builds a temperature from month and whether the hour is midday, plus Gaussian noise;
- sets a base kWh by band (night ~1.2, morning peak ~5.5, working hours ~3.5, evening peak ~6.5);
- multiplies by 0.7 on Saturday/Sunday (`dayofweek >= 5`);
- multiplies by 1.15 if temperature > 25 °C and by 1.20 if temperature < 0 °C;
- applies uniform noise about ±12%.

`previousConsumption` is **not** the true lag of the previous hour. It is `base * Uniform(0.85, 1.05)`. So it is a noisy copy of the same underlying level. That makes the feature very informative and is one reason R² is so high. A real lag feature would use the previous timestamp’s actual kWh and would be weaker, and more honest.

### 6.3 Features and target

| Feature | Meaning |
|---------|---------|
| hour | 0–23 |
| dayOfWeek | 0 = Monday … 6 = Sunday (pandas convention) |
| month | 1–12 |
| temperature | °C |
| previousConsumption | kWh (see caveat above) |

Target: `energyConsumption` (kWh for that hour).

Random Forest does not need feature scaling. Categorical fields are stored as integers, which trees can split on.

### 6.4 Training setup

- Algorithm: `RandomForestRegressor`
- `n_estimators=100`, `max_depth=10`, `random_state=42`, `n_jobs=-1`
- Split: 80% train, 20% test, same `random_state`
- Persist with joblib to `models/energy_model.pkl`

Depth 10 is a regularisation choice so the forest does not grow fully until pure leaves. 100 trees is a default that is good enough for 2,160 rows; more trees would mainly raise training time.

I did not run a grid search or k-fold in the submitted code. A stronger methodology would compare at least linear regression and maybe one boosted tree, and would use time-based splitting (train on earlier days, test on later days) instead of a shuffled split. Shuffling hourly data leaks the same seasonal pattern into both sides of the split.

### 6.5 Test-set scores (re-run on this machine)

Command: `python -m app.model` in `AI-Service`.

| Metric | Value |
|--------|--------|
| MAE | 0.1193 kWh |
| RMSE | 0.1695 kWh |
| R² | 0.9914 |

**How to read this.** MAE is the average absolute miss. On a series whose peaks are around 5–6.5 kWh, 0.12 kWh is a small error **on this generator**. RMSE is higher than MAE, which means some hours are off by more than the average (squares punish those). R² near 1 means almost all variance in the test slice is explained by the five features.

**Why the number is not a trophy.** The target is a noisy function of those same features. The model is approximating a formula it could almost have been given in closed form. In Ahmad et al., even a good HVAC model on a real hotel had RMSE of several kWh, not 0.17. If this system were connected to a real meter, I would expect R² to drop a lot unless occupancy, weather quality and device-level series were added.

### 6.6 Inference service

FastAPI app: `/health`, `/predict`. Input schema matches the C# DTO field names (camelCase in JSON). If the pickle file is missing, `prediction.py` trains on first use.

### 6.7 Recommendation rules

Let `p` be predicted kWh and `a` the average of all `EnergyReadings`.

| Condition | Type | Intent of the message |
|-----------|------|------------------------|
| p > 1.20 a | HIGH | Peak / HVAC / shift load |
| p > 1.05 a | MODERATE | Slightly high, switch unused devices |
| 0.90 a < p ≤ 1.05 a | NORMAL | Stay as you are |
| p ≤ 0.90 a | LOW | Positive feedback |

The percentage shown in the text is `(p - a) / a`. Thresholds 5% / 20% are design choices, not estimated from data. Comparing a **single hour** to the **global average** (all hours, all devices) is crude: night hours will often look LOW and evening hours HIGH even when they are normal for that hour. A better rule would compare against the average for the same hour of week.

### 6.8 Fallback predictor (when Python is down)

Hour factors: night 0.6, morning 1.4, day 1.0, evening 1.6, other 0.9. Temperature: ×1.15 if > 25 °C, ×1.20 if < 5 °C. Weekend: ×0.75 if `DayOfWeek` is 0 or 6.

There is a small inconsistency: Python training uses pandas Monday=0, and the Vue form also uses Monday=0. The fallback treats 0 and 6 as weekend, i.e. Monday and Sunday. Saturday (5) is not reduced. I would fix that in a revision (`DayOfWeek` 5 and 6). Until then, the fallback is slightly wrong on Saturdays.

## 11. Results and discussion

The application meets FR1–FR8 in a local demo. The model meets its own test set with MAE 0.1193 kWh and R² 0.9914. The UI is clear enough for a supervisor to operate without a script, which matches the positive comment on the interface.

The weak part is not the screens; it is **how far the numbers can be trusted** and **how little automated testing exists**. High R² is largely an artefact of how the CSV is built. Recommendations compare one hour to a global mean, so they are blunt. Authentication was skipped on purpose. Daily dashboard charts can disagree with the seed calendar.

Those points are the ones to improve if the report and the product are extended: real or public dataset (e.g. a building from an open repository), walk-forward evaluation, hour-of-week baselines for recommendations, a flag for fallback, and a small API test project.

The project is a complete chain: SQL readings, Vue monitoring, .NET API, Python Random Forest, stored forecasts and rule-based advice. The architecture is ordinary but clear, which was the point.
